## 1. Summary

Every edit to an editable plan becomes undoable and redoable through one
in-memory history for the page visit:
- place, move and remove
- pin ("Counts toward")
- a check answer
- a specialisation or capstone choice
- "Completed through"

You get there three ways: Undo/Redo icon buttons beside "Completed
through", Cmd/Ctrl+Z and Cmd/Ctrl+Shift+Z (and Ctrl+Y), or the existing
toast. The toast now appears for every edit, offers Redo after an undo,
and keeps Phase 03's knock-on warning. It extends Phase 03's single
`runAction` path to the four edit kinds that still call the API directly.
It exists because the 8-second toast was too short to read and act on.
The audience is ANU Advanced Computing students editing their own plan.

## 2. Requirements

### 2.1 Functional requirements

The requirements are **UR1–UR16 in `specs/2026-09-29-undo-redo.md` §2.1**,
copied by reference so there's only one source. In brief:

- UR1: every edit kind above is undoable and redoable.
- UR2: an edit that changes nothing records no step and shows no toast.
- UR3–UR5: one linear history for the page visit, in memory. A new edit
  clears redo. At most 50 steps.
- UR6: each kind's inverse (listed in the spec).
- UR7: if an undo or redo fails, it's announced and the step stays put.
- UR8: all seven kinds go through `runAction`.
- UR9: one change in flight at a time; Undo/Redo are disabled meanwhile.
- UR10: every edit, undo and redo shows the one toast, rewritten in place.
- UR11: the exact message for each kind, plus the knock-on warning.
- UR12: after an undo the toast reads "Undid: …" and offers Redo. After a
  redo it offers Undo again.
- UR13: header icon buttons named by their next action, disabled when
  there's nothing to do.
- UR14: the read-only plan has no buttons and ignores the shortcuts.
- UR15: the shortcuts.
- UR16: shortcuts are ignored in text-entry fields (and, from Phase 04,
  while the palette is open).

One addition from planning: a cutoff message at every semester reuses
`completedReadout(...).short`, "All semesters completed" (UR11 names the
other two readouts).

### 2.2 Non-functional requirements

- axe is clean with the buttons enabled and disabled, and with the toast

- No horizontal overflow at 390×844 and 1920×1080. The header row keeps

- merging runs of edits
- undoing plan creation, "Copy plan link" or UI state
- a history list

This plan also leaves out:

## 4. Approach

**Actions and steps (pure, `plan-actions.ts`).** `PlanAction` gains `pin`,
`check`, `choice` and `cutoff`. `UndoEntry`/`undoEntry` become
`HistoryStep`/`historyStep`, whose inverse is a list, so a remove's
inverse is place-then-pin with no special field:

```ts
export interface HistoryStep { message: string; redo: PlanAction; undo: PlanAction[] }
```

**History (pure, new `undo-history.ts`).** An immutable `{ past, future }`
with `recordStep`, `undoStep` and `redoStep` (a 50 cap), plus the pure
shortcut helpers `historyShortcut` and `isTextEntry`.

**Planner.**
- `viewRef` and `historyRef` mirror state, so work run from a queue reads
  the latest values.
- One promise chain (`queueRef`) runs edits, undos and redos in order.
  `busy` (a count of queued or running work) disables Undo/Redo.
- Toast state becomes `{ mode: "edit" | "undone"; message: string; knockOn:
  string }`:
  - "edit" offers Undo.
  - "undone" shows "Undid: <message>." and offers Redo.
- Buttons, toast and shortcuts all call the same `undo()` and `redo()`.
- If a multi-part inverse fails partway, the view is set to the last good
  result, the error is announced, and the step stays in `past`. Placing
  is an upsert and pinning sets a value, so re-trying the same inverse is
  safe.
- Client refusal (`dropTargets`) applies to fresh place and move edits
  only. Undo and redo re-apply states the plan already had in this
  session, and the server remains the authority (UR7).

Alternatives rejected in the spec §4: partial toasts, merging runs, a
header status line, and persistent history. Keeping `UndoEntry.restorePin`
alongside a single `undo` action was rejected: seven kinds with ad-hoc
extra fields is harder to apply uniformly than a list of inverses.

**Execution rule.** If an existing spec's click is intercepted by the
now-more-frequent toast (it sits at z-index 45 bottom-centre, over the
details panel on phones), treat that as a real UX finding and stop and
report it. Don't dismiss the toast or add waits to route around it.

      `historyRef` and `queueRef = useRef<Promise<void>>(Promise.resolve())`.
    - `commitView(next: PlanView)` sets both `view` and `viewRef`.
      `commitHistory(next: History)` sets both `history` and `historyRef`.
    - `enqueue(work: () => Promise<void>): Promise<void>` increments
      `busy`, chains onto `queueRef`, and decrements in `finally`.
    - `runAction(action)` returns `enqueue(...)` around today's body.
      That body reads `viewRef.current`, records `historyStep` with
      `recordStep`, and shows the toast `{ mode: "edit", message:
      step.message, knockOn }`.
    - `undo(): Promise<void>` enqueues this: take the last `past` step and
      apply `step.undo` in order.
      - On an error: `commitView` the last good result, announce the
        error, and show the toast in "edit" mode for that step again.
      - Otherwise: `commitHistory(undoStep(...))` and show `{ mode:
        "undone", message: step.message, knockOn:
        knockOnText(newlyBroken(before, after, actedOn(step.redo))) }`.
    - `redo(): Promise<void>` enqueues this: take the last `future` step
      and apply `step.redo`. On success, `commitHistory(redoStep(...))`
      and show "edit" mode with the step's message and knock-on.
    - The toast:
      - reads `{mode === "undone" ? "Undid: " : ""}{message}.{knockOn}`
      - its button is "Undo" (calls `undo`) or "Redo" (calls `redo`),
        disabled while `busy > 0`, reading "Undoing…"/"Redoing…" when
        pending
      - keeps the hover/focus hold and `startUndoTimer`
    - Delete `handleUndo` and `undoPending`.
